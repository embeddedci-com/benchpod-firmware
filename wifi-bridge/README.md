# BenchPod Wi-Fi bridge firmware

Firmware for the small Ethernet-to-Wi-Fi box that gives a BenchPod v4 (which has no radio) a
Wi-Fi uplink: an **ESP32-WROOM-32E-N8** with a **LAN8742A** PHY, clipped to the pod, powered from
its USB-A port. The bridge's USB-C is **power only**; everything else goes through the pod.
Hardware rev A: benchpod-private `pcb/wifi-bridge` (generated by
`tools/gen_schematic.py`); design: benchpod-private `enclosure/wifi-bridge.md`.

> **Status: build-verified and host-tested only. Nothing here has run on hardware yet** (rev A is
> not ordered and there is no ESP32 Ethernet board on the bench). See "What is verified".

## What it does

```
 pod ==RJ45== [LAN8742A]--RMII--[ESP32 EMAC]   l2fwd   [Wi-Fi STA, MAC = pod MAC] ))) AP
                                    |  EtherType 0x88B5: control channel (never forwarded)
                          UART0 -- Tag-Connect TC2030 pads: factory flashing, debug console
 USB-C: 5 V only
```

- **Layer-2 bridge for one MAC.** The source of the first Ethernet frame becomes the pod MAC.
  The Wi-Fi station takes that MAC and joins the stored network, so the router sees the pod
  itself: DHCP, ARP, mDNS and the cloud connection behave as on a wire. Frames to and from any
  other MAC are dropped. After an Ethernet link-down a different device may take over.
- **No IP address, no open ports, no SoftAP.** No esp_netif or lwIP interface exists; frames go
  through the raw Wi-Fi path (`esp_wifi_internal_tx` / `esp_wifi_internal_reg_rxcb`) and the EMAC
  in promiscuous mode.
- **Managed by the pod, over the network.** Once the bridge is flashed, Wi-Fi setup, status and
  firmware updates all go through the control channel on EtherType 0x88B5 (Ethernet side
  only): HELLO every 2 s, STATUS, SCAN, SET_WIFI / CLEAR_WIFI, signed OTA, REBOOT,
  FACTORY_RESET. Spec: [docs/PROTOCOL.md](docs/PROTOCOL.md). The user sets Wi-Fi with the pod's
  `set-wifi` / web Settings, never on the bridge itself.
- **Paired with one pod.** The first pod that pairs is trusted (trust on first use); the key is
  agreed with X25519 and never sent. After that the bridge only obeys requests signed with that
  key (HMAC-SHA256, per-boot nonce, replay counter), and the Wi-Fi passphrase only arrives
  encrypted (XChaCha20). A separate **PAIR button** makes it forget the pod and pair with the next
  one.
- **Robust OTA:** two OTA app slots plus a read-only factory image, signed images only, and a
  trial boot: a new image keeps itself only after it has handled a control request from the
  pod; otherwise it reboots after 120 s and the bootloader returns to the previous image (see
  "Firmware updates").
- **FACTORY button** as the last resort: held 5 s at power-up, the bootloader wipes the
  settings and pairing and boots the factory image, even if both OTA images are broken (see
  "Buttons and recovery").
- **Minimal UART console** on the TC2030 pads, for factory test and debugging (below).
- **Security:** encrypted passphrase storage and secure boot in production builds:
  [docs/SECURITY.md](docs/SECURITY.md).

## Build

ESP-IDF v5.5 in Docker, the same pinned image as `../esp32-hosted-slave` (`idf-image`, by
digest). Docker is Colima on the Mac.

```sh
./build.sh                # dev build -> build/benchpod-wifi-bridge.bin (signed with the dev key)
./build.sh production     # secure boot v2 + flash encryption -> build-prod/ (unsigned, see SECURITY.md)
./build.sh menuconfig     # any other idf.py command
```

The first dev build creates `keys/dev_signing_key.pem` (git-ignored). A bridge accepts OTA images
only when they are signed with the same key as the image it runs, so keep that file if you want
to update dev bridges over the network.

Build-time options (`idf.py menuconfig` → *BenchPod Wi-Fi bridge*): RMII clock source
(oscillator on GPIO0, or the GPIO17 output option with R15 fitted and X1 not fitted), PHY
address (0), Wi-Fi country (`US`, channels 1-11), HELLO interval, the run-time factory-reset hold
time, and how long a new image waits for the pod before it rolls back. The power-up factory
reset is the bootloader's (`CONFIG_BOOTLOADER_FACTORY_RESET*`, `CONFIG_BOOTLOADER_HOLD_TIME_GPIO`
in `sdkconfig.defaults`).

## Flash (factory and bench)

The bridge has no USB data and no BOOT/RESET buttons: UART0, EN and GPIO0 are only on the
**Tag-Connect TC2030** pads (J2). J2 follows the ESP-Prog program header pin order (1 EN, 2 3V3,
3 TXD0, 4 GND, 5 RXD0, 6 IO0), so you need:

- an Espressif **ESP-Prog** (USB to UART with DTR/RTS auto-reset), and
- a **Tag-Connect TC2030-IDC** cable (the legged version), plugged into the ESP-Prog's **PROG**
  header (not JTAG), pin 1 to pin 1.

Power the bridge from the ESP-Prog (PROG VDD jumper on 3.3 V) with USB-C unplugged, **or** from
USB-C with the ESP-Prog's VDD jumper removed, never both. The ESP-Prog resets the ESP32 into the
ROM loader and back by itself.

```sh
brew install esptool        # once (or: pip3 install esptool); esptool runs on the host
./build.sh                  # in Docker
./flash.sh                  # finds the ESP-Prog's UART port, flashes, opens the log
./flash.sh --erase          # same, but erase everything first (no Wi-Fi settings, no pairing)
./flash.sh -p /dev/cu.usbserial-XXXX1 --no-monitor
```

The ESP-Prog shows up as two ports (an FT2232H). Channel A is JTAG; the UART is channel B, the
second one (`/dev/cu.usbserial-<serial>1` on macOS, `/dev/ttyUSB1` on Linux). `flash.sh` picks
it when the ESP-Prog is the only adapter plugged in. Without `flash.sh`:

```sh
cd build && esptool --chip esp32 -p /dev/cu.usbserial-XXXX1 -b 460800 write_flash @flash_args
```

Offsets: bootloader 0x1000, partition table 0x10000, otadata 0x17000, app 0x20000 (the
**factory** partition). The factory image is written only here and never by OTA, so flash the
release you want users to fall back to. After the factory flash every update goes over the
network into ota_0/ota_1 (below).

Without an ESP-Prog, any 3.3 V USB-UART on TXD0/RXD0/GND works for the log. For flashing you
then have to pull IO0 (pad 6) to GND while pulsing EN (pad 1) to GND by hand, because there are
no buttons.

The image signs itself with this checkout's dev key (`keys/dev_signing_key.pem`). A bridge
flashed from here only accepts OTA images built from here, so keep that key for the first boards.

## Bring-up checklist (first rev A boards)

Nothing below has been tried on hardware yet. Go in order: each step needs the one before. Log
lines are what the firmware prints at 115200 (`./flash.sh --monitor`); the debug console takes
commands on the same port (`help`, `status`). Steps 5-12 use a Linux laptop on the RJ45 as the
"pod" (`tools/bridgectl.py`); step 13 swaps in a real pod.

1. **Power.** USB-C only, no ESP-Prog VDD: 3V3 test pad 3.3 V, idle draw about 0.1 A
   (0.5 W budget). Then switch to ESP-Prog power for flashing.
2. **ROM loader and flash.** `./flash.sh --erase`. If esptool cannot connect: check the pin 1
   orientation of the TC2030, the PROG (not JTAG) header, and that GPIO0 reaches the ROM loader
   (R11 pull-up, R12 470 ohm in series).
3. **Boot.** Expect `bridge: benchpod-wifi-bridge 0.1.0, hardware rev A` and
   `ota: running benchpod-wifi-bridge 0.1.0 from factory`. A boot loop or download mode on a
   normal reset means GPIO0 is held low: X1 must be tri-state while OE (GPIO32) is low.
4. **RMII clock and PHY.** Expect `eth: started, bridge MAC …, PHY addr 0`. `EMAC init failed
   (no RMII clock?)` means no 50 MHz on GPIO0: scope PHY_CLKIN and OE (GPIO32 high after boot).
   A PHY timeout means a wrong address (pad MDC/MDIO) or nRST (GPIO4) not released.
5. **Link.** Plug in the laptop: `eth: link up`, RJ45 LEDs on, then `eth: pod MAC learned:
   <laptop MAC>`. `status` on the console shows `ethernet: up` and the `pod-mac`.
6. **Control channel and pairing.** On the laptop: `sudo tools/bridgectl.py -i eth0 hello`
   (HELLO every 2 s, flags without 0x20), then `pair` (`ctl: paired with pod …`), then
   `status`. TP8 stops toggling at 10 Hz once paired.
7. **Wi-Fi join with the pod MAC.** `bridgectl.py -i eth0 set-wifi "<ssid>" "<pass>"`.
   Expect `wifi: station MAC -> <laptop MAC>`, `wifi: state joining`, `wifi: state connected`,
   TP8 high. The router's client list must show the laptop's MAC, not an Espressif one.
8. **Forwarding.** The laptop gets a DHCP lease from the router through the bridge; ping, then
   mDNS (`dns-sd -B _services._dns-sd._udp` or `avahi-browse -a`) to check multicast both ways.
   `status` counters: `wifi_tx` and `eth_tx` climbing, `wifi_tx_err` and `eth_tx_err` near 0.
9. **Throughput.** iperf3 from the laptop to a wired host behind the AP, both directions. The
   target is at least 10 Mbit/s; tune the buffer counts in `sdkconfig.defaults` if it is short.
10. **OTA and rollback.** Bump `PROJECT_VER`, `./build.sh`, `bridgectl.py -i eth0 ota
    build/benchpod-wifi-bridge.bin`. Expect `ota: image verified`, a reboot, `ota: new image
    on trial`, then `ota: new image confirmed by the pod` after the next `bridgectl status`.
    Then repeat without sending anything for 120 s: `rebooting to roll back`, and the old
    version comes back. An image built with a different key must fail with `ota-verify`.
11. **Buttons.** PAIR: `ctl: pairing forgotten`, TP8 at 10 Hz, `bridgectl pair` works again.
    FACTORY held 5 s while running: `creds: Wi-Fi credentials cleared`. FACTORY held while
    plugging in USB-C for 5 s: the bootloader log shows the factory reset, and the bridge
    comes up from `factory`, unpaired, without Wi-Fi.
12. **Recovery paths.** Unplug the cable (`eth: link down`) and plug in a second laptop
    (`pod MAC changed to …`, Wi-Fi restarts with the new MAC). Reboot the AP: the bridge
    reconnects on its own.

13. **With a pod.** Flash a development build of the pod firmware (`make -C stm32h563`, the
    default `WIFI_BRIDGE=1`), press PAIR on the bridge (it is paired with the laptop), and cable
    it to the pod. Pod log: `[bridge] Wi-Fi bridge found: …`; pod console `bridge` shows
    `paired`, then `wifi-set "<ssid>" "<pass>"` and `wifi-show` (`via: wifi-bridge`). The pod
    gets its DHCP lease, mDNS name and cloud connection over Wi-Fi.

Record results, and anything changed, in this section or in the PR that fixes it.

## Firmware updates

The pod relays a signed image over the control channel: OTA_BEGIN (erases the inactive slot),
1024-byte OTA_DATA chunks in order (a lost ack is safe to retry, a gap is answered with the
expected offset), OTA_END (checks SHA-256, the RSA-3072 signature and the project name, then
selects the new slot), REBOOT.

```
ota_0 [running, confirmed] --OTA--> ota_1 [new] --reboot--> ota_1 on trial (FLAGS 0x10 in HELLO)
   pod sends any request within 120 s  -> ota_1 confirmed, ota_0 kept as the fallback
   no request (Ethernet or control path broken, crash loop) -> reboot -> bootloader runs ota_0
(the first update after the factory flash goes factory -> ota_0, with the factory image as fallback)
```

A crash or watchdog reset during the trial also falls back, because the bootloader only gives a
pending image one boot. The pod confirms simply by talking to the bridge after the reboot (it
sends STATUS anyway to read the new version); if HELLO still shows the old FW_VERSION, the
update rolled back. The trial timeout is `CONFIG_BRIDGE_CONFIRM_TIMEOUT_S`.

`tools/bridgectl.py -i eth0 ota build/benchpod-wifi-bridge.bin` does the same from a Linux
machine wired to the bridge.

## Buttons and recovery

Two buttons, so pairing a new pod can never wipe settings by accident:

| Button | Gesture | Done by | Effect |
|---|---|---|---|
| PAIR (GPIO35) | a press | app (`main/board.c`) | Forgets the paired pod; the next pod that sends PAIR is trusted. Wi-Fi settings stay. TP8 toggles at 10 Hz until a pod pairs. For "new or replaced pod". |
| FACTORY (SW3, GPIO34) | hold 5 s **while running** | app (`main/board.c`) | Clears the Wi-Fi credentials, keeps the pairing and the firmware, no reboot. TP8 toggles at 10 Hz from 1 s of holding until 2 s after the clear. For "wrong network / moved house". |
| FACTORY (SW3, GPIO34) | hold while **powering up** (plug in USB-C, keep holding 5 s) | bootloader (`CONFIG_BOOTLOADER_FACTORY_RESET`) | Erases `nvs` (Wi-Fi credentials **and pairing**) and `otadata`, then boots the **factory** image. Works when both OTA images are broken, as long as the bootloader and the factory image are intact. |

Pairing in normal use needs no button: plug the bridge into the pod and the pod pairs on first
contact. Press PAIR only when the bridge should obey a different pod (the old one is gone or
broken); the new pod then pairs on its next HELLO. The FACTORY_RESET control message and the
console `factory-reset` also clear the pairing; `clear-wifi` and the running FACTORY gesture do
not.

Recovery flow when the bridge stops working (no HELLO, no Wi-Fi):

1. Power-cycle it (the pod can switch its USB-A port). A broken new image rolls back by itself.
2. Still dead: hold FACTORY, plug in power, keep holding 5 s, release. The bridge boots the
   factory firmware with no Wi-Fi settings and no pairing; the pod sees HELLO without the paired
   flag.
3. The pod pairs again on its own (first contact). Set Wi-Fi again from the pod (`set-wifi` /
   Settings). The pod then offers the current bridge firmware, which goes into ota_0 as a
   normal, rollback-protected update.

Notes: the bootloader samples FACTORY on every boot, so holding it through a software reboot
also triggers it. The board has no LEDs, so the user gets no feedback on the bridge itself: the
pod shows the result (old firmware version, not paired, no Wi-Fi), and TP8 shows it to a scope. GPIO34 is input-only with no internal pull: the bootloader's pull-up
call does nothing there and R20 (10k to 3V3) keeps the line high; an open or missing R20 would
read low at every boot and reset the bridge each time, so check R20 in production test. PAIR
(GPIO35) is also input-only and relies on R41; C27 debounces it, and the firmware needs it low
for 50 ms. A stuck-low PAIR would unpair once per press-and-release cycle, never in a loop.

## Pins (rev A)

| Function | GPIO | Notes |
|---|---|---|
| RMII TXD0/TXD1/TX_EN | 19/22/21 | fixed |
| RMII RXD0/RXD1/CRS_DV | 25/26/27 | fixed |
| RMII REF_CLK in | 0 | from X1; also the boot strap (R11 pulls it high while X1 is off) |
| Oscillator OE | 32 | pulled down; firmware enables it before the EMAC starts |
| PHY nRST | 4 | pulled down; released by the driver after the clock runs |
| MDC / MDIO | 23 / 18 | PHY address 0 |
| STATUS test pad TP8 | 13 | output, see "STATUS test pad" |
| unused | 14, 33 | no LEDs on the board (Ethernet link/activity: the RJ45's own LEDs) |
| FACTORY button | 34 | active low, external pull-up R20; hold 5 s running (Wi-Fi) or at power-up (factory image) |
| PAIR button | 35 | active low, external pull-up R41 + 100 nF C27; a press forgets the paired pod |
| UART0 TX / RX | 1 / 3 | TC2030 pads only (with EN, BOOT = GPIO0, 3V3, GND) |
| Alternative clock out | 17 | only with R15 fitted and X1 not fitted |

Before every reboot the firmware stops the oscillator and holds the PHY in reset, so GPIO0 reads
high if the straps are sampled again.

## STATUS test pad (TP8, GPIO13)

The board has no status LEDs (Ethernet link and activity are on the RJ45). GPIO13 drives test
pad TP8 for a scope or logic analyser; the first matching row wins:

| TP8 | Meaning |
|---|---|
| 10 Hz square wave | a button acted (2 s after a PAIR press or a FACTORY Wi-Fi clear), FACTORY held for more than 1 s, or not paired (waiting for a pod's PAIR) |
| 2 Hz square wave | OTA transfer in progress |
| high | Wi-Fi connected |
| 1 Hz, 50 % | joining |
| 1 Hz, 10 % (100 ms high) | wrong passphrase or SSID not found, retrying |
| 100 ms high every 2 s | credentials stored, waiting for the first frame from the pod |
| low | no Wi-Fi credentials (or the app is not running) |

## Debug console (UART0 on the TC2030 pads, 115200 8N1)

For factory test and debugging, not for users: they configure Wi-Fi through the pod. Line-based;
every command ends with `OK` or `ERR <message>`, data lines first. Quote values with spaces
(`"my network"`). `log off` hides log lines and `echo off` the character echo, for a factory
test script.

```
> version
benchpod-wifi-bridge 0.1.0 hw A
OK
> status
state: connected
ssid: lab net
channel: 6
rssi: -58
bssid: 60:00:00:00:00:01
ethernet: up
pod-mac: 00:80:e1:12:34:56
bridge-mac: 24:0a:c4:00:00:03
ota: idle
paired: yes
image: confirmed
uptime: 125
counters: eth_rx=812 wifi_tx=790 wifi_tx_err=0 wifi_rx=1204 eth_tx=1150 eth_tx_err=0 dropped=76
OK
```

Commands: `help`, `version`, `status`, `scan`, `set-wifi <ssid> [passphrase]` and `clear-wifi`
(bench bring-up without a pod), `unpair` (same as the PAIR button), `reboot`, `factory-reset`,
`log on|off`, `echo on|off`. The console is not subject to pairing: it is on the internal pads. There is
no firmware update over the console: updates are network-only, and the pads plus esptool are the
factory path.

## What is verified

| | Status |
|---|---|
| Builds with ESP-IDF v5.5 (pinned image), no warnings in our code | yes: app 0xB1000 bytes (35% of the 2 MB factory slot), IRAM 78%, DRAM 21% static |
| Production overlay (secure boot v2, flash encryption, NVS encryption) builds; bootloader fits before 0x10000 | yes (bootloader 0xC000 with the factory-reset code, 0x3000 to spare) |
| Protocol codec, forwarding and learning rules, tokenizer, OTA sequencing, image check, pairing state machine, request signing (HMAC-SHA256 against RFC 4231 vectors, tampering, replay, reboot, rotation) | host tests (`make -C test`, 297 checks, ASan/UBSan) |
| Python client codec and signing match the C encoder byte for byte | `tools/test_bridgectl.py` |
| Anything on hardware: RMII clock and PHY bring-up, link, forwarding, Wi-Fi join with the pod MAC, multicast (mDNS) delivery through the station, throughput, OTA + signature check + trial boot and rollback, the PAIR button and both FACTORY gestures (bootloader factory reset on GPIO34 included), pairing with a real pod, console on the TC2030 pads, TP8 patterns | **not tested** |
| eFuse flows (secure boot, flash encryption): irreversible, try on a sacrificial board | **not tested** |

Things to watch at bring-up:

- **EMAC init needs the clock.** `esp_eth_mac_new_esp32` fails ("EMAC init failed (no RMII
  clock?)") if X1 does not run: check OE on GPIO32 and that X1 is a tri-state part.
- **PHY address and strap.** The LAN8742A must come up in REF_CLK In mode (nINTSEL high, R29).
- **Multicast through the station.** mDNS discovery of the pod over Wi-Fi depends on the AP
  delivering group frames to the station and the driver passing them up the raw rx path.
- **Throughput.** The target is >= 10 Mbit/s; buffer counts in `sdkconfig.defaults` follow
  ESP-IDF's iperf example, untuned. `esp_eth_transmit` is serialised by a mutex shared by the
  Wi-Fi rx path and the control task.
- **Scan while connected** drops traffic briefly while the radio leaves the channel.
